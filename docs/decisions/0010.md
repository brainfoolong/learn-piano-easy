# 0010: The end-to-end tests walk a sample of the course, and CI shards them before each deploy

## Decision

- The two course walks play `sampleLessons`: the fewest lessons that hold every step kind and role.
- The layout walk measures each sampled lesson twice: a phone in dark German, and a desktop in light English.
- `src/learn/model.test.ts` proves every lesson of the course valid, without a browser.
- CI runs the end-to-end tests in shards on parallel runners, one browser each. `ci.yml` names how many.
- A push to main deploys the site to GitHub Pages only once the checks and every shard have passed.

This replaces the rejection of fewer layout combinations in decision 0006.

## Why

The suite took about 30 minutes of browser time, and the two course walks were 82% of it.
They walked about 50 lessons, and the layout walk drew each one in eight combinations.
The lessons are data, and a unit test already checks each one. The browser adds proof only once per kind of step.
German's longer words stress the narrow page, and each theme needs drawing once, so two views keep the checks that find flaws.
Every push now deploys the site, so CI's time is the wait before a fix goes live.

## Consequences

- A new step kind or role adds a lesson to both walks with no new code.
- A layout flaw seen only in one theme at one width may pass the walk. The page's own layout tests still cover it.
- A Playwright test that only CI's software WebGL breaks fails a shard, and blocks the deploy.

## Rejected

- **Keeping every lesson in the walks:** it bought no coverage the unit test and one lesson per kind lack.
- **More workers on one runner:** decision 0001 measured four workers in CI's image slower than one.
- **Deploying without the end-to-end tests:** a broken player would reach every learner.
